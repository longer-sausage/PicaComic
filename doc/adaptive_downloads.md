# 动态下载并行

在「设置 → APP → 其它」中新增「动态调整下载并行」，新安装及旧配置升级均默认开启。
关闭后显示原来的手动并行数，保留此前选择；切换模式或手动数值立即影响后续请求，
正在传输的请求正常完成。下载列表显示当前并行上限。

图片和 E-Hentai 压缩包共用 `DownloadTaskScheduler`。自动模式从 6 路开始，范围为
1–16，每 2 秒采样网络吞吐量、首次数据响应延迟和失败情况。有足够待下载内容时逐步
增加并行数；探测未带来至少 8% 的吞吐收益，或响应明显变慢且收益不足时回退，并等待
一段时间再探测。超时、429、503 会降低并行数，429/503 同时暂停发送新请求，遵守
`Retry-After`。失败图片单独进行带抖动的指数退避，最多重试 4 次；永久性 4xx 直接报错。

下载池按完成事件补位，失败任务在池外等待重试。图片完成后立即累计进度，连续页检查点
与乱序完成记录同时保存，兼容旧队列；新记录使用 `章节:页码` 避免编号碰撞。暂停取消
本任务的网络请求，不清除阅读器的全局加载记录。图片流结束后才复制最终文件，避免
最后一块网络数据到达时缓存尚未写完。章节元数据最多 3 路并行获取，结果保留章节顺序。

图片连接池复用 HTTP 连接；并发首次请求共用一次适配器初始化。队列快照按 200 ms
合并，暂停和后台到期时立即保存。压缩包以 4 MiB 分块、256 KiB 缓冲写入，每 500 ms
合并检查点，校验 HTTP 范围和已提交字节；不支持分块时回退为单流下载。快速暂停再继续
会等待旧后台任务保存并关闭文件，避免两个任务同时写同一压缩包。

## 验证

```shell
flutter test --no-pub
dart run tool/benchmark_downloads.dart
```

2026-11-11，Windows / Dart 3.9.2 本机合成 HTTP 测试：600 个 256 KiB 响应，合计
150 MiB，每个请求首次数据延迟 100 ms、后续数据块间隔 10 ms。在同一调度器上，固定
6 路耗时 14.344 s，自动模式耗时 10.057 s，最高探测到 10 路，耗时减少约 30%。
这组结果只反映该模拟链路，真实收益取决于源站限流、网络带宽、图片处理和磁盘速度。

测试覆盖并行补位、自动增减、限流退避、单图片重试、乱序进度恢复、旧队列迁移、
暂停取消、归档并行写入的文件校验、忽略 Range、未知文件长度和归档快速暂停恢复。
